# Internationalization & Localization

## 1. Purpose

This document defines the internationalization (i18n) and localization (l10n) architecture of the project.

The goal is to provide a predictable, scalable, and provider-agnostic way to manage:

- Translated application content.
- Translation keys.
- Languages.
- Regional locales.
- Number, currency, and date formatting.
- Translation management platforms.
- Runtime language selection.
- Fallback behavior.

Internationalization is considered a cross-cutting infrastructure concern.

Business features should consume the project's i18n abstractions without depending directly on the translation management platform or implementing their own localization mechanisms.

---

## 2. Core Principle

Translation, locale, and timezone are independent concerns.

```text
Language     → What language the user reads
Locale       → How regional values are represented
TimeZone     → In which timezone date/time values are displayed
```

For example:

```text
language: en
locale: en-GB
timeZone: Europe/Madrid
```

The application may therefore display English translations while formatting numbers, currencies, and dates according to British conventions and displaying instants in the user's current timezone.

These concepts MUST NOT be treated as interchangeable.

---

# 3. Internationalization vs Localization

## Internationalization — i18n

Internationalization concerns translated application content.

Examples:

```text
Save      → Guardar
Cancel    → Cancelar
Sign in   → Iniciar sesión
```

Translation catalogs are organized primarily by language:

```text
en
es
de
fr
```

Example:

```json
{
  "common.save": "Save",
  "common.cancel": "Cancel",
  "auth.login.title": "Sign in"
}
```

i18n answers:

> What language should the application speak?

---

## Localization — l10n

Localization concerns how values are represented according to regional conventions.

Examples include:

- Number formatting.
- Decimal separators.
- Thousands separators.
- Currency.
- Percentages.
- Dates.
- Regional date conventions.

For example:

```text
en-US → 08/11/2026
en-GB → 11/08/2026
```

or:

```text
en-US → $1,234.56
es-ES → 1.234,56 €
```

l10n answers:

> How should information be represented for this user's region?

---

# 4. Language and Locale MUST Be Separate

The application MUST NOT assume that a language uniquely determines a locale.

For example:

```text
language = en
```

does not tell us whether the user expects:

```text
en-US
en-GB
en-CA
en-AU
```

Therefore the application models these independently.

Conceptually:

```ts
interface LocalizationContext {
  language: string;
  locale: string;
}
```

Timezone is intentionally not part of this concern and is defined separately in `datetime.md`.

A complete user context may ultimately contain:

```ts
interface UserRegionalContext {
  language: string;
  locale: string;
  timeZone: string;
}
```

but each concern remains architecturally independent.

---

# 5. Translation Catalog Strategy

Translation catalogs SHOULD be organized by language unless actual linguistic differences require regional variants.

Preferred:

```text
i18n/
├── en.json
├── es.json
├── de.json
└── fr.json
```

Avoid duplicating complete catalogs such as:

```text
en-US.json
en-GB.json
en-AU.json
```

only because regional formatting differs.

Formatting differences belong to localization, not translation.

Regional translation variants MAY exist when the actual wording differs significantly.

For example:

```text
en
└── common.json

en-GB
└── overrides.json
```

This should be an exception rather than the default.

---

# 6. Translation Keys

Translation keys are part of the application's source contract.

They SHOULD be:

- Stable.
- Semantic.
- Predictable.
- Independent of the translated text.
- Organized by domain or feature.
- Suitable for automated validation.

Prefer:

```text
auth.login.title
auth.login.submit
auth.errors.invalidCredentials

users.profile.title

common.actions.save
common.actions.cancel
common.actions.delete
```

Avoid using the source text itself as the key:

```text
"Save"
"Cancel"
"Invalid credentials"
```

Avoid arbitrary identifiers:

```text
label1
message23
text_login_4
```

The key should communicate intent, not presentation.

---

# 7. Ownership of Translation Keys

Features own their domain-specific translation keys.

For example:

```text
auth.*
users.*
orders.*
planning.*
```

Truly reusable application terminology belongs to shared namespaces:

```text
common.*
validation.*
navigation.*
```

A translation SHOULD NOT be moved into `common` merely because it appears more than once.

Shared translations represent shared semantics, not simple textual duplication.

This prevents `common` from becoming an uncontrolled global translation namespace.

---

# 8. Translation Management Platform

Tolgee is the preferred Translation Management Platform for the project.

Tolgee provides capabilities such as:

- Translation management.
- Collaborative translation.
- Translation review.
- Developer tooling.
- Machine-assisted translation.
- Translation synchronization.
- APIs and automation.

However:

> Tolgee is infrastructure, not application architecture.

Business features MUST NOT depend directly on Tolgee-specific APIs.

The architecture should conceptually remain:

```text
Business Feature
       │
       ▼
Project i18n API
       │
       ▼
Translation Runtime
       │
       ├── Translation catalogs
       │
       └── Tolgee
```

This allows the Translation Management Platform to evolve without redesigning business features.

Possible alternatives could therefore be introduced in the future without changing feature architecture.

---

# 9. Source of Truth

Translation keys and their usage originate from application source code.

Translation catalogs MUST remain versionable artifacts compatible with Git-based development and CI.

Tolgee MUST NOT become the only place where the application's translation contract exists.

The expected lifecycle is conceptually:

```text
Developer
    │
    ▼
Translation key
    │
    ▼
Repository
    │
    ▼
Tolgee
    │
    ▼
Translation / Review
    │
    ▼
Translation catalogs
    │
    ▼
Application
```

Synchronization details are implementation concerns and may evolve independently.

---

# 10. Runtime Language Resolution

Language selection SHOULD follow a deterministic resolution strategy.

Conceptually:

```text
Explicit user preference
        ↓
Application/account preference
        ↓
Browser preference
        ↓
Application default
```

For example:

```text
user preference → es
browser          → en
default          → en

resolved         → es
```

The resolved language should be available through a central application-level abstraction.

Individual features MUST NOT independently determine the active language.

---

# 11. Locale Resolution

Locale follows a similar but independent resolution strategy.

Conceptually:

```text
Explicit user locale
        ↓
Account/application configuration
        ↓
Browser locale
        ↓
Application default
```

Example:

```text
language: en
locale: en-GB
```

Changing the locale MUST NOT necessarily change the translation language.

---

# 12. Fallback Strategy

Translation resolution MUST have deterministic fallback behavior.

For regional translation variants:

```text
en-GB
 ↓
en
 ↓
default language
```

For example:

```text
requested language: en-GB

1. en-GB override
2. en
3. application default
```

Missing translations SHOULD be visible during development and testing rather than silently hidden.

Production behavior should remain safe and predictable.

---

# 13. Formatting

Application features SHOULD NOT manually implement regional formatting.

Avoid logic such as:

```ts
value.toLocaleString('es-ES');
```

scattered throughout business features.

Formatting should use the application's localization infrastructure.

This applies to:

- Numbers.
- Percentages.
- Currency.
- Dates.
- Other locale-sensitive values.

Features provide the semantic value.

Infrastructure determines its regional representation.

---

# 14. Date/Time Boundary

Locale formatting and timezone conversion are different responsibilities.

This architecture does not define how timestamps are stored, transported, or converted.

Those rules belong to:

```text
docs/architecture/datetime.md
```

The i18n/l10n layer may determine how a resolved date is displayed:

```text
11/08/2026
August 11, 2026
11 August 2026
```

but it MUST NOT independently decide what instant in time that value represents.

---

# 15. Angular Integration

The project SHOULD leverage Angular's localization and formatting capabilities where they provide appropriate primitives.

Third-party tooling SHOULD be introduced where Angular's native capabilities do not cover the required runtime translation workflow.

The architecture MUST NOT expose Angular-specific or Tolgee-specific implementation details unnecessarily to business features.

Features should consume stable project-level APIs.

---

# 16. Nx Architecture

Internationalization infrastructure belongs to the platform/shared infrastructure layer rather than individual business domains.

Conceptually:

```text
libs/
├── platform/
│   └── i18n/
│
└── features/
    ├── auth/
    ├── users/
    └── ...
```

The exact library structure is an implementation decision and may evolve.

Business features MAY define and own their translation resources while relying on the centralized runtime infrastructure.

---

# 17. Lazy Loading

The architecture SHOULD allow translations to follow feature boundaries.

Large applications SHOULD NOT be forced to load every translation for every domain during application bootstrap.

Conceptually:

```text
Application
   │
   ├── common translations
   ├── auth translations
   │
   └── feature translations
            ↓
       loaded when needed
```

This becomes particularly important as the application grows and supports federation-ready deployment.

Translation resources SHOULD therefore respect feature/domain boundaries where practical.

---

# 18. Testing

The i18n architecture MUST be test-friendly.

Tests SHOULD NOT require access to Tolgee or another external translation service.

The project SHOULD provide lightweight testing utilities capable of:

- Resolving translation keys.
- Providing deterministic languages/locales.
- Detecting missing keys where appropriate.
- Testing components without network dependencies.

Example conceptually:

```ts
provideTestingI18n({
  language: 'en',
  locale: 'en-GB',
});
```

The exact API belongs to implementation specs.

---

# 19. CI Validation

The project SHOULD eventually automate validation of the translation contract.

Potential validations include:

```text
✓ referenced keys exist
✓ catalogs are structurally valid
✓ required languages contain required keys
✓ orphaned keys can be detected
✓ invalid namespaces can be detected
```

Translation correctness should therefore be enforceable by tooling rather than relying exclusively on manual review.

---

# 20. AI-Assisted Development

Translation architecture should be deterministic enough for both humans and AI coding agents.

AI agents MUST be able to determine:

- Where a translation key belongs.
- How a key should be named.
- Which language contains the source translation.
- How new translations are introduced.
- Which APIs features are allowed to consume.

AI-generated code SHOULD NOT:

- Hardcode user-facing text when translation is required.
- Invent alternative translation mechanisms.
- Access Tolgee directly from business features.
- Duplicate existing translation keys unnecessarily.
- Mix timezone logic with locale formatting.

These rules should later be enforceable through project instructions, architecture validation, and automated checks.

---

# 21. Architectural Rules

The following rules are considered architectural constraints.

### Rule 1

User-facing application text MUST be internationalizable unless explicitly excluded.

### Rule 2

Language and locale MUST be modeled independently.

### Rule 3

Timezone MUST remain independent from language and locale.

### Rule 4

Business features MUST NOT depend directly on Tolgee.

### Rule 5

Translation keys SHOULD be semantic and domain-oriented.

### Rule 6

Shared translation namespaces MUST represent shared semantics, not merely duplicate strings.

### Rule 7

Regional formatting MUST NOT be manually scattered throughout business features.

### Rule 8

Translation resolution and locale resolution MUST be centralized.

### Rule 9

Tests MUST NOT depend on an external translation service.

### Rule 10

Translation resources SHOULD respect feature boundaries and support lazy loading.

### Rule 11

Translation catalogs MUST remain compatible with version control and automated validation.

---

# 22. Non-Goals

This document intentionally does not define:

- The exact Tolgee SDK configuration.
- CI synchronization commands.
- Exact Nx library names.
- Exact Angular providers.
- Translation extraction scripts.
- Concrete testing helpers.
- Deployment-specific translation loading.
- Exact caching strategy.

Those details belong in implementation specifications and, where appropriate, ADRs.

---

# 23. Summary

The project's internationalization architecture is based on a simple separation:

```text
Translation
    │
    └── Language
         en / es / de / ...

Localization
    │
    └── Locale
         en-GB / en-US / es-ES / ...

Date & Time
    │
    └── TimeZone
         Europe/Madrid / America/New_York / ...
```

Tolgee is the preferred translation management platform, but it remains an infrastructure detail.

The application architecture owns the translation contract.

The result should be an i18n/l10n system that is:

- Predictable.
- Testable.
- Provider-agnostic.
- Feature-oriented.
- Git-friendly.
- Automation-friendly.
- AI-friendly.
- Suitable for enterprise Angular applications.
